Plate II · End-to-End Flow

From question to answer.

What happens when an advisor types “what was the Smith family's portfolio performance last quarter?” — in plain language, eight steps, no jargon. Each step explains who is doing what and why.

🔒
Always scoped to who's asking
An advisor can only see their own book. A client can only see their own accounts. Enforced by the database, not by the AI.
📋
Every step is recorded
Who asked, what they asked, which data sources answered, what was returned. Regulator-grade audit trail by default.
⚖️
Compliance owns the rules
Which questions are allowed, which data is sensitive, what gets redacted — configured by compliance, not engineering.
Plate II · On-Behalf-Of Token Chain

How identity survives every hop.

The single most important flow to get right in this architecture, because everything else — row-level security in Snowflake, audit trails, advisor-vs-client scoping — depends on the user identity surviving every hop. Traced end to end below.

A sequence in ten movements. The user's Entra token is never forwarded as-is — it is exchanged at every boundary, with the user assertion threading all the way through to Snowflake's row-access policies.

!
Why this flow is load-bearing
If identity breaks at any hop, three things fail at once: row-level security can no longer scope advisors to their book, audit trails lose the user attribution regulators require, and advisor-vs-client scoping collapses into "trust the LLM to ask correctly" — which is precisely the threat model OBO exists to defeat.

User→ Entra→ Chat UI
User authenticates against Entra ID. The chat UI receives an access token whose audience is the UI's own app registration — not Foundry, not yet.

Call Foundry with user token
Chat UI→ Foundry
UI exchanges its token for one with audience = Foundry, then sends it as a Bearer token. The user's identity is in the sub and upn claims.
aud = Foundry   ·   sub = user.upn
iii
Foundry validates & binds run
Foundry
Foundry validates signature, expiry, and audience. Extracts user claims and binds them to the thread and run. Every event in this run will carry the user identity in its trace.
iv
Agent emits tool call
Foundry→ MCP gw
The agent decides it needs performance.get_twr. The orchestrator hands the call to the MCP gateway along with the user context.
v
First OBO exchange · gateway → Performance MCP
MCP gw→ Entra→ MCP gw
The gateway presents its own managed identity credentials plus the user's token as an assertion to Entra. Entra issues a new token whose audience is the Performance MCP and whose subject is still the user.
aud = api://perf-mcp   ·   sub = user.upn   ·   azp = mcp-gw
vi
Call domain MCP with OBO token
MCP gw→ Performance MCP
JSON-RPC over MCP. The Performance MCP receives the call with the freshly-minted token in the Authorization header.
vii
Domain MCP validates & checks scope
Performance MCP
The MCP independently validates the token, then enforces its own scope check — even though the gateway already let the call through. Defense in depth: every hop verifies independently.
viii
Second OBO exchange · MCP → Snowflake
Performance MCP→ Entra→ Performance MCP
Now the MCP needs a Snowflake-bound token. It presents its own managed identity plus the original user assertion. The user identity threads through — it is re-presented, not regenerated.
aud = snowflake   ·   sub = user.upn   ·   azp = perf-mcp
ix
Snowflake MCP brokers session
Performance MCP→ Snowflake MCP→ Snowflake
The Snowflake MCP applies pooling, warehouse routing, query timeouts. The session it opens uses Snowflake's external OAuth security integration — CURRENT_USER() resolves to the actual person.
x
Row-access policy fires
Snowflake
Policies on holdings, transactions, accounts reference CURRENT_USER() to filter to the advisor's book. The database — not the application — enforces entitlement. If identity ever broke upstream, this returns empty: the safe failure mode.
At every step
log { user.upn, agent_id, run_id, tool, args, result_hash, timestamp } → immutable audit store, joinable across hops by run_id.
Plate III · MCP Gateway · Component View

Inside the chokepoint.

The MCP gateway shown as a single box on Plate I is in fact a small system. Three concerns: a request pipeline that every tool call traverses, a set of registries the pipeline reads from, and operational services that wrap both.

§
How to read this plate
A request enters from Foundry's agent runtime at the top, flows through the request pipeline left-to-right, and exits to a domain MCP at the bottom. The pipeline reads from registries on its way through and reports to operations the whole time.
